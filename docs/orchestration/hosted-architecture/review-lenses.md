# Four-lens review: the hosted architecture design

Reviewed: [the hosted architecture design](../../specs/2026-11-25-hosted-architecture-design.md)
(called "the spec" below), read once as the owner, with
[the plan](../../plans/penguin-slicer-plan.md) as its declared prerequisite. Only the spec
is reviewed; the plan is quoted where the spec disagrees with it. Line numbers are the
spec's unless a path says otherwise.

Path prefix used in the findings: `spec` =
`docs/specs/2026-11-25-hosted-architecture-design.md`.

## Lens 1: the set agrees with itself

- spec:8 — "the plan, whose terms this document uses unchanged" — the spec changes three of the plan's terms: the configuration (plan line 36: it holds the pairing code and, in phase 4, is a file in the Onshape account whose secrets never reach the server; spec lines 159-161: one JSON document in the state bucket that "holds no secret", with "Nothing here changes" in phase 4 at line 339), the pairing code (plan line 58: an administrator puts it in the configuration; spec line 205: used once and typed in by a user) and the administrator (spec line 51) — replace the sentence with "these three plan terms change here" and one line per term saying what replaces the plan's meaning, including that the Onshape-account configuration file of phase 4 is dropped.
- spec:16 — "Two containers on Railway behind Cloudflare." — the plan calls phase 3 "the same hosted on AWS" (plan lines 21, 282-300) and asks "Which AWS service runs the slice service"; the spec never says it replaces AWS with Railway, so the reader meets a contradiction with the document they were told to read first — say in the Short answer that Railway replaces the plan's AWS and that the plan's phase 3 title and questions are to be updated.
- spec:9 — "This document settles the questions the plan lists under phase 3 and the security questions under phase 5" — three of those questions get no answer anywhere in the spec: "How a new Orca version is rolled out to the hosted slice service" (plan line 329), "What the daemon stores on the daemon's computer" (plan line 410), and for daemon telemetry "what proves a message comes from a paired daemon", "what a message must never hold" and "its size and rate limits" (plan line 412) — answer each, or name them at line 9 as left to a phase's own spec.
- spec:27 — "A **group** is the set of users who share one configuration and one printer" — elsewhere a group has several printers: "one record of its paired printers" (line 25), the "Paired printers" row (line 102), and the plan's configuration holds "the printers" (plan line 36), while the configuration document holds "the printer's display name" (line 161) and the record holds "the daemon's id" (line 214), both singular — decide whether a group has one printer or several and make the group definition (lines 27 and 41), the record and the configuration document say the same.
- spec:42 — "**front container** | The Railway service that runs the wizard's server side and the relay, in one process." — the same name is then used for the process on one machine, where there is no Railway service or container: the development identity is what "the front container signs in when, and only when, it listens on the loopback address" (line 48) and phase 2 runs "with the development identity" (line 334); the plan's names for that actor are "the wizard's server side" and "caller" — define the front container as the process (the wizard's server side and the relay together) wherever it runs, and say that hosted it is one Railway service; do the same for the slice container, or use the plan's "the wizard's server side" in the phase 2 sections.
- spec:47 — "**owner key**" — "owner" already names the person who owns the project ("the owner's coding agents", line 32; "a document the owner writes into the state bucket", line 170), so one word names two things, and line 301 ("The owner's coding agents read the log bucket") sits a section away from "under its user's owner key" (line 263) — rename the term (for example "user key"), since line 265 shows it is derived from the signed-in user.
- spec:22 — "The server keeps a part or a sliced file for two hours at most" — repeated at line 263 ("for two hours at most") and line 272 ("the parts and sliced files of the last two hours"), but the part store keeps a part "for two hours after it was last used" (line 46), so a part that is sliced repeatedly stays indefinitely — write "two hours after its last use" in all three places.
- spec:25 — "Nothing else outlives a restart." — the log bucket's files outlive a restart for ninety days (line 104), line 108 says "Only the two buckets must survive", and the bullet's own heading says "a bucket" where there are two — reword the bullet to name both buckets and what each keeps.
- spec:104 — "Ninety days | Not lost" — line 305 says "Lines written in the minute before a crash may not have reached the log bucket"; they survive only in Railway's log view, for seven days (line 290) — put that exception in the table cell.
- spec:83 — "so the split adds no code" — the split is the stated reason for at least one new route ("a route from which the front container fetches its log lines", line 316, needed because "the slice container has no credentials to write them itself", line 293) and for "the proxying of parts, slice jobs and sliced files" (line 326) — say what the split does add.
- spec:76 — "The design uses nothing particular to Railway" — the design relies on Railway's log view as the only copy of the last minute's lines after a crash (line 306) and on Railway's private network as the slice container's only protection (line 72), and "one EC2 instance" (line 77) contradicts the reason for two containers given at lines 79-81 — list what a move must replace (the private network, the seven-day log view) and say whether the move keeps the two containers apart.
- spec:279 — "There are five: the Onshape app's client id and secret, the key that encrypts the cookie, the relay's secret key, and the two buckets' credentials." — the list gives five only if the client id and secret count as one and each bucket's credentials as one, and it omits the read-only credential for the log bucket of line 301, which is not "an environment variable of the front container" (line 281) — number the list, and state the read-only credential as the sixth with where it lives.
- spec:31 — "A daemon waits on a held request" — the same thing is "held sync" from line 49 on — write "held sync" in the Short answer.
- spec:26 — "on the standalone page" — the plan's name for this is "a page reached directly from a browser" (plan line 123) or "outside Onshape" (plan lines 242-244); "standalone page" appears only at lines 26 and 179 — use the plan's wording or add the term to the Terms table.
- spec:179 — "which companies they belong to; those companies are the user's groups" — the group is defined at lines 28 and 41 as "an Onshape company or classroom", and as the user alone when they belong to no company; here classrooms and the group of one are dropped — make the sentence match the definition, and say whether Onshape's sign-in answer reports classrooms.
- spec:196 — "The hosted front container uses real Onshape sign-in from its first day, which needs an Onshape OAuth app registered in phase 3." — the plan places both in phase 4: the wizard's server side "signs users in through Onshape (phase 4)" (plan line 66) and the Onshape app registration is a phase 4 resource (plan lines 333-334, 351) — say that this moves sign-in and the app registration from the plan's phase 4 to phase 3.

## Lens 2: nothing is assumed beyond the declared prerequisites

- spec:232 — "a delivery job, a cancel or a granted start for that daemon" — "granted start" is defined neither here nor in the plan (the plan has only "start command") — add one sentence saying what a granted start is, or drop it and link printer delivery's guide.
- spec:103 — "As printer delivery's guide says | As printer delivery's guide says: a print already started goes on" — the row's two answers live only in a document the reader is not told to read, and line 107 promises "each row says what the user sees then"; this is also the row a restart of the front container hits — state in the row how long a delivery job and the printer's status are kept and what the user sees after a restart, and link the guide's section.
- spec:44 — "holds each group's configuration and paired-printer record" — "paired-printer record" is used eight times (lines 44, 211, 219, 276, 322 among them) and described only at line 214; it is not in the Terms table — add it to the Terms table with its one-sentence meaning.
- spec:210 — "The relay links the user's current group to that daemon" — "current group" is used here and at line 219 as a term but is never named; line 172 says only "uses one at a time" — add "current group" to the Terms table, or name it at line 172.

## Lens 3: the facts that matter, in prose

- spec:16 — "Two containers on Railway behind Cloudflare." — no fact supports choosing Railway over the AWS the plan names; lines 76-77 say only that leaving is easy — add the one or two facts that decided it (cost, the effort of running it, the private network).
- spec:70 — "Cloudflare proxies it and holds no logic of PenguinSlicer's." — no reason is given for having Cloudflare at all, yet it sets two of the design's constraints (the 100 MB request body at line 115, the 125 seconds at lines 233 and 251) — add the fact that makes Cloudflare worth those limits.
- spec:81 — "The split also keeps Orca's memory spike, and a redeploy of the slicer, from dropping every daemon's connection." — the spec gives no fact about the opposite case: a restart or redeploy of the front container drops every held sync, every progress stream and every delivery job in the relay's memory, and the reader cannot tell what a user or a daemon sees then — add what happens (see also the finding on line 103).
- spec:88 — "The front container needs well under 1 GB." — no fact is behind the figure, though the front container streams sliced files of up to 14.1 MB and holds one thread per daemon — add the measurement or reasoning, or move it to "To confirm before building on it".
- spec:238 — "which is enough for the first few dozen daemons" — no fact carries "a few dozen", and line 243 asks for "enough threads" without a number — give the thread count the front container's server is set to and how it yields the figure.
- spec:357 — "About $7 to $40 a month by Railway's published rates, depending on how much slicing is done." — the figure does not say what it covers (both containers, the buckets, Cloudflare) nor how much slicing each end of the range assumes — state both.
- spec:187 — "The cookie holds the user's identity, groups and Onshape tokens, and is encrypted" — the claim that one cookie can carry all of this for thirty days (line 100) has no fact behind it: a browser cookie is limited to about 4 KB, and nothing says how long Onshape's tokens last or how they are renewed — add the sizes and Onshape's token lifetime, or list it under "To confirm before building on it".

No passage piles up identifiers or paths without saying what they show, so nothing needs
moving to a details file; no details file exists and none is needed.
